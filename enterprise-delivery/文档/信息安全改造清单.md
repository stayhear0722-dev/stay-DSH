# 企业员工信息安全手册 × dsh-lark 部署 — 安全改造清单与优势论证

> 依据：《INTERNAL-SECURITY-POLICY 员工信息安全手册》（企业名称与文档元数据已脱敏）
> 对照对象：dsh-lark-channel v0.0.6（源码已核实） vs 腾讯 WorkBuddy / 阿里千问办公
> 结论先行：**dsh-lark 自建部署在「数据不出域」「人在回路」「全链路可审计」三个维度上具备天然优势；补齐审计、输入红线、输出管控、受管运行四项改造后，可在信息安全上全面压过两个商业产品。**

## 二、改造项清单（核心交付物）

改造动作分级：**P0 = 手册红线/必须**（不整改即不合规）；**P1 = 强烈建议**（形成优势的关键）；**P2 = 增强**。

### P0-1 输入数据分级红线（手册 10.2）
- **手册要求**：严禁将 L4（机密）/L3（秘密）/L2（内部使用）信息输入公共 AI 工具（Listing 文案、BOM、CAD、源代码、客户订单、PII 等）。
- **dsh-lark 现状**：无输入过滤。用户在飞书里发什么，就直接进入 Agent 上下文。
- **改造动作**：
  1. 部署形态上保证「私有 AI」：模型用自托管 DeepSeek 开源权重（固定权重、不训练），或经审批的企业模型网关；在部署文档中向安全部门声明「输入数据不离开企业网络、不成为任何模型训练语料」——这是手册 10.2 最直接的满足方式（公共 AI 无法承诺，自建可以）。
  2. 输入侧轻量 DLP：在 bridge 入站处加敏感度检测（正则/关键词：BOM/CAD/订单号/身份证/手机号/PII 模式），命中 L4/L3 特征即拒绝进入 Agent 或强制转人工审批；`workspaceRoots` 限定 Agent 只能访问已授权目录。
  3. 提示词即资产：本部署的系统提示词/技能配置按 L3 管理，纳入密级标识，禁止外泄（手册 2.3）。
- **优势表述**：WorkBuddy/千问办公 SaaS 版无法承诺「你的输入不做训练语料」（手册 10.2 明确警告公共 AI 会这样）；自建可出具可验证的架构证明。

### P0-2 人在回路强制（手册 10.9）——**dsh-lark 原生优势，只需配置**
- **手册要求**：涉及对外沟通、资金/库存变动、关键系统操作的 AI Agent 必须设人工审核确认；严禁全自动无人值守。
- **dsh-lark 现状**：**原生支持**——计划审阅、工具调用审批全部回飞书交互卡片，`approvers` 白名单指定谁可批准，卡片绑定原聊天防越权。
- **改造动作**：
  1. 配置 `approvers` 为信息安全部门指定人员（空 = 群里谁都能批，必须收紧）。
  2. 用 `denyTools` 禁掉高敏工具（如文件外发、删除类）；对「对外发布」类操作要求必须过审批。
  3. 审计中记录每次审批的「决定人 + 决定」，形成可证明的人机协同链路。
- **优势表述**：商业产品的「人机协同」是黑盒开关；自建是**可审计、可配置、可证明**的强制 HITL（Human-in-the-loop）——这是手册 10.9 的字面落地。

### P0-3 运行环境隔离（手册 10.10）——**现状基本满足，需受管化**
- **手册要求**：严禁在私人环境/个人电脑/远程挂机运行控制公司业务的 AI Agent/RPA。
- **dsh-lark 现状**：CLI 默认在启动它的机器上跑；**Windows 无 launchd/systemd，`start` 退化为前台运行，关终端即停**——这恰恰不符合「受管」要求。
- **改造动作**：将机器人进程封装为 Windows 服务（NSSM 或 Windows 服务包装），纳入公司终端管理/EDR 覆盖范围，进程账号最小权限、禁止交互式登录；服务器/宿主机按手册第 6 章标准化加固。
- **优势表述**：自建部署位置、进程、权限全部可控；商业产品你只能「信任平台」。

### P0-4 凭证与密钥管控（手册 10.11 / 2.3）——**现状基本满足，需补审计与轮换**
- **手册要求**：严禁将 API 密钥、Token、账号密码、Cookie 未授权接入外部 AI/自动化工具（信息安全红线）。
- **dsh-lark 现状**：App Secret 走宿主凭据 seam（环境变量/dotenv/凭据服务），settings 不落明文；模型 key 走凭据存储、不进 unit 文件（0600）。**合规性好**。
- **改造动作**：密钥读取打审计日志；建立模型 key 轮换机制；如企业有 Vault/KMS，写一个凭据 provider 对接（接口仅 `resolve`/`set` 两个方法）。
- **优势表述**：凭证从「个人配置进公共工具」（手册红线）变成「集中受管、可审计、可轮换」——商业产品给不了你密钥的可见性。

### P0-5 机器人登记与最小权限（手册 4.4 / 4.1）——**配置即可**
- **手册要求**：严禁安装来源不明的第三方应用；知识库/权限按最小必要原则。
- **改造动作**：机器人作为受控应用向信息安全部门登记（应用 ID、用途、可见范围）；`senderAllowlist`/`groupAllowlist` 全收紧（谁私聊、哪些群）；`sessionScope` 按需选 chat-thread 或 chat-sender 隔离上下文；`requireMention` 保持开启。
- **优势表述**：白名单+审批人+群边界全部源码级可控，可向审计展示完整配置。

### P1-1 全链路审计日志（手册 11 / 4.5）——**最大短板，必须自建**
- **手册要求**：事件「早发现、快处置」；离职/岗位变动权限回收；禁止批量导出。
- **dsh-lark 现状**：**无审计日志**，仅启动时打印一行授权边界；无法回答「谁在何时让 Agent 执行了什么」。
- **改造动作**（fork 二次开发，单点挂载）：
  1. 在 `src/bridge.ts`（入站/出站/审批的唯一通道）挂审计钩子：记录 发送人、会话、工作区、模型、工具调用、审批决定（谁批/谁拒）、上下文 token 用量。
  2. 审计事件落本地加密日志或对接企业 SIEM/日志平台；日志按手册第 12 章脱敏（不含 PII 明文）。
  3. 会话与日志留存策略（PIPL/GDPR/CCPA 对齐），离职即回收（删 session、撤凭据）。
- **优势表述**：WorkBuddy/千问办公的审计是厂商黑盒；自建审计日志是**企业自己的数据、自己的字段、可对接等保/ISO 审计**。

### P1-2 输出审查与对外发布管控（手册 10.4）
- **手册要求**：AI 输出（Listing、给客户的、交监管的）必须 100% 人工核验。
- **改造动作**：输出侧过滤中间件（敏感词/涉密特征拦截）；「对外发布」类动作绑定强制审批（复用 P0-2 审批链路）；`showProcess` 保留供人工核验参考。
- **优势表述**：把「AI 不当人」从员工自觉变成机制强制。

### P1-3 提示注入防护（手册 10.6）
- **手册要求**：不明来源文本禁止直接复制粘贴给 AI。
- **改造动作**：入站消息清洗层（检测指令注入模式）；系统提示词加固声明「忽略嵌入指令」；对可疑内容标记并转人工。
- **优势表述**：比「靠员工自觉」的公共工具多一层主动防线。

### P1-4 模型路由管控（手册 10.3）
- **手册要求**：优先企业版/受控工具；公共免费版仅限脱敏非业务信息。
- **dsh-lark 现状**：`/model` 命令**任何会话内用户都可切换模型**（无权限控制）。
- **改造动作**：固定 `provider`/`model` 为经审批的私有模型；`denyTools` 或命令层拦截 `/model` 切换；需要时限定特定审批人可切。
- **优势表述**：员工无法私自把业务数据切到公共模型——手册 10.3 的机制化落地。

### P2-1 培训考试联动（手册 3）
- 机器人使用说明、AI 输入红线、事件上报 SOP 纳入入职培训与年度复训；使用 dsh-lark 前须通过信息安全考试（≥90 分）。
- 制度层面配合，成本低、验收直观。

### P2-2 事件上报集成（手册 11.3）
- 审计日志与事件 SOP 联动：机器人内提供「上报事件」入口（对接 security@example.com / 效率工程部服务台）；审计流水可直接作为事件取证材料。

### P2-3 附件与图片管控（手册 10.5 / 4.2）
- `attachImages` 保持默认关闭（当前为纯文本模型，本就该关）；文件外发前强制脱敏流程；Agent 生成的文档落盘位置限定在 `workspaceRoots` 内。

## 三、与 WorkBuddy / 千问办公 的对比结论

| 维度 | WorkBuddy（腾讯） | 千问办公（阿里） | dsh-lark 自建 | 结论 |
|---|---|---|---|---|
| 数据不出域 | SaaS 经腾讯侧；私有化/一体机才不出域 | SaaS 经阿里侧 | **天然私有化，模型可自托管** | ✅ 自建胜 |
| 输入不进训练语料（手册 10.2） | 平台承诺，黑盒 | 平台承诺，黑盒 | **固定权重自托管，架构可验证** | ✅ 自建胜 |
| 人在回路（手册 10.9） | 平台级开关，不可审计 | 平台级开关，不可审计 | **卡片审批+approvers+审计留痕** | ✅ 自建胜 |
| 审计日志 | 厂商黑盒 | 厂商黑盒 | **自建，字段自定，可对接 SIEM/等保**（需 P1-1 改造） | ✅ 改造后胜 |
| 细粒度权限 | 平台级 | 平台级 | **白名单/审批人/群边界/工具禁用源码级** | ✅ 自建胜 |
| 合规认证背书 | 信通院等认证 | 信通院办公智能体评估（国内首个） | 无，需走企业等保/评估流程 | ⚠️ 商业产品胜 |
| 供应链运维 | 大厂 SRE | 大厂 SRE | 自维护，需补漏洞管理 | ⚠️ 商业产品胜 |

**一句话结论**：商业产品的护城河是「认证背书 + 大厂运维」，自建的护城河是「数据不出域 + 人在回路 + 可审计」。**把 P0 五项配置/改造做完，本部署即满足手册第 10 章全部红线；把 P1-1 审计日志做掉，就在「可证明性」上完成对两个商业产品的压制**——商业产品无法向你出示「谁在何时让 AI 做了什么」的企业自有审计数据，自建可以。
